## 임베딩 차단 상세 (정직 기록)

| 시도 | 구성 | 결과 |
|---|---|---|
| A9 사전검증 | 단일 호출 ×2 | 성공 (768d) |
| end-to-end 1차 | batch_size=100 → 93개 한 요청 | 실패 (429) |
| 1차 직후 진단 | 단일 호출 ×1 | 성공. **per-request 배치 한계** 시사 |
| end-to-end 2차 | batch_size=1 + 429 지수 backoff(6회) | 실패. 첫 단일 호출부터 429 → **일일 쿼터 소진** |

→ 두 종류의 한계로 보인다: (1) 한 요청에 93개 배치는 과대(단일은 동작), (2) 반복 시도 누적으로 **free-tier 일일 쿼터 소진**. 후자는 코드로 해결 불가(계정/플랜 문제).

## 해결 및 완료 (2026-06-06)

- **재시도 시점 진단**: 06-06 오전(KST) 재실행도 첫 호출부터 429. 원인은 RPD(일일 쿼터) 미리셋. Gemini RPD는 **태평양 자정**에 리셋되는데 한국 06-06 오전은 태평양 기준 아직 06-05라 같은 쿼터 윈도우. 분당 한도였다면 backoff 90초 중 통과했어야 하나 전 시도 429 → RPD 소진 확정
- **선택한 해결책 (b) 유료 티어**: GCP billing 활성화 → 동일 `GOOGLE_API_KEY`가 Tier 1로 승격(키 교체 없음). 코드·배치 설정 변경 없이 그대로 재실행.
- **결과**: 임베딩 93/93 성공, Chroma 적재 93청크. 파이프라인 반환값 `{'chunks':93,'embedded':93,'stored':93}`.
- **독립 검증**: 적재 직후 종료 → 새 프로세스로 `ChromaStore("chroma_db")` 재오픈 → `count()==93`, 샘플(`SRVO-001_058`) 임베딩 차원 768d, 메타데이터(`error_code/page_no/content_type/severity_hint` 등) 정상.
- **비용**: gemini-embedding-001 $0.15/1M tok, 93청크 수만 토큰 → 1센트 미만.

## 결론

- **코드는 정상**: 파싱은 261p→93청크 실데이터로 동작, 임베딩/적재 로직은 단위 테스트 28개 통과. embedder는 설계대로 **fail-loud**(429를 조용히 삼키지 않고 backoff 후 예외 전파).
- **end-to-end 실행 완료**: 실제 임베딩+적재까지 전량 완주(93청크). 1차(06-05) 미완은 코드가 아니라 free-tier 일일 쿼터였고 유료 티어 전환으로 해소. "구현"과 "전량 인덱싱 실행" **둘 다 충족**
- **남은 미검증**: 최적 배치 크기(아래 후속). batch_size=1로 완주했으므로 production 인덱싱 자체엔 지장 없음.

## 후속 보강 (이번에 반영)

- `embedder`에 **429 지수 backoff 재시도 + 배치 간 지연**, 기본 `batch_size=1`(단일 호출 검증분) 적용. 비-429 오류는 즉시 전파.
- **최적 배치 크기는 미검증**: "1은 동작, 93은 429"까지만 확인. 쿼터 있는 키로 안전 배치 상한을 추후 측정해야 함(A9 후속).
